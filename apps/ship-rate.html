Ship rate · pull requests, people and machines

For each repository: how many pull requests were opened, merged and closed in each time box, what share of the ones resolved were merged, and how much of the volume came from people versus coding agents.

How it works

How it works

Everything on this page is one named view, asked at load for each repository you compare. There is no database of your pull requests behind it and nothing was copied in advance: the view reads GitHub when it runs, and the page draws what comes back.

1. The data

Pull requests arrive through the github realm's issue door — GitHub's issues/list-for-repo, where every pull request is also an issue — as Issue nodes of the shared dev vocabulary carrying isChangeRequest, openedAt, mergedAt, closedAt and authorKind. GitHub narrows the read itself to records updated since the window's start, up to 4,000 of them per repository. The door caches each read for five minutes, so a merge that happened in the last few minutes may not be counted yet; press Refresh after that and it will be.

authorKind is computed by the producer from the record, and these are its definitions:

human
a user account, with no agent marker in the pull request's description.
assisted
a user account whose description carries a Co-authored-by: line naming a coding agent (Copilot, Claude, Devin, Codex, Cursor, Aider, Jules, Sweep, Gemini, ChatGPT, OpenAI) or the Generated with [Claude Code] footer.
agent
a bot account whose login names one of those agents.
bot
any other bot account, or a record performed through a GitHub App (Dependabot, release bots).

A pull request an agent wrote with no marker counts as human: the realm reports what the record declares and does not guess. embabel/embabel-agent labels no pull request by author, so labels play no part here; if a repository adopted such a label the producer's rule, not this page, is where it would be read.

2. The questions

One view, GitHubChangeRequestThroughput(repo, period, since, until): for the pull requests of repo touched since since, one row per period and author kind, plus an all row per period. This page computes since at load as the start of the period that is N periods before the current one (12 weeks, 12 months, 6 quarters or 1 year back) and leaves until empty, so the current period is shown as it stands and labelled so far. The latest complete period fills the four tiles; the change shown under each is against the period before it.

The columns: opened, merged and closedUnmerged count events in the period they happened, so a pull request opened in March and merged in April is in both months, and a period's merges may exceed its openings. mergedPctOfResolved is merged ÷ (merged + closed without merging) × 100 — the merge rate on this page — and meanHoursToMerge is the mean from opening to merge for the pull requests merged in the period. The machine share on a tile is (assisted + agent + bot opened) ÷ all opened.

The Virtual Cypher that runs, exactly as the realm declares it:

MATCH (:GitHubRepository {full_name: $repo})-[:HAS_ISSUE]->(pr:Issue)
WHERE pr.updatedAt >= $since
WITH pr, pr.isChangeRequest AS isPr, pr.authorKind AS authorKind, pr.openedAt AS openedAt, pr.mergedAt AS mergedAt, pr.closedAt AS closedAt
WHERE isPr = true
UNWIND [{at: openedAt, event: 'opened'}, {at: mergedAt, event: 'merged'}, {at: CASE WHEN mergedAt IS NULL THEN closedAt ELSE null END, event: 'closed'}] AS ev
WITH authorKind, openedAt, mergedAt, ev
WHERE ev.at IS NOT NULL AND ev.at >= $since AND ($until = '' OR ev.at < $until)
UNWIND [authorKind, 'all'] AS kind
WITH toString(date.truncate($period, datetime(ev.at))) AS period, kind,
     sum(CASE ev.event WHEN 'opened' THEN 1 ELSE 0 END) AS opened,
     sum(CASE ev.event WHEN 'merged' THEN 1 ELSE 0 END) AS merged,
     sum(CASE ev.event WHEN 'closed' THEN 1 ELSE 0 END) AS closedUnmerged,
     avg(CASE WHEN ev.event = 'merged' THEN duration.inSeconds(datetime(openedAt), datetime(mergedAt)).seconds / 3600.0 ELSE null END) AS meanHoursToMerge
RETURN period, kind AS authorKind, opened, merged, closedUnmerged, merged + closedUnmerged AS resolved,
       CASE WHEN merged + closedUnmerged = 0 THEN null ELSE round(100.0 * merged / (merged + closedUnmerged), 1) END AS mergedPctOfResolved,
       CASE WHEN meanHoursToMerge IS NULL THEN null ELSE round(meanHoursToMerge, 1) END AS meanHoursToMerge
ORDER BY period, authorKind

The pr.updatedAt >= $since line is what GitHub applies: any of the three events after since moved the record's updated_at past it, so the read is a superset and the graph applies the exact window per event afterwards.

3. When it looks wrong

  • A card says no pull requests were touched. The window excludes them, or the repository name is not one the appliance's GitHub credential can see. Widen the time box first; then check the name on GitHub.
  • A card says the read was incomplete. More than 4,000 issues and pull requests were touched in the window, so every count on that card is a lower bound and every mean describes only what was read. Choose a shorter time box.
  • A card shows an error. The view did not complete: GitHub was unreachable or rate-limited, or the appliance has no GitHub credential. The message is the server's own; nothing on the card is from a previous load.
  • A period is empty in the middle of the chart. Nothing was opened, merged or closed in it. The page draws every period in the window, including the empty ones.
  • The current period looks low. It is labelled so far and is not complete; compare complete periods with each other.
  • A number differs from GitHub by a few minutes' worth of activity. The five-minute cache. Press Refresh after it expires.

4. What made this possible

  • The author-kind label is computed inside the producer that fetches the record, so every view and every question asked of the realm sees the same classification; on a conventional stack that is a batch job with its own staleness window and its own definition to keep in step.
  • The time box is a parameter of one view, not four views: date.truncate($period, …) buckets inside the query, so week, month, quarter and year are the same read and the same arithmetic.
  • This page asks the world by view name at load. There is no backend to deploy, and the same view answers the same question in the realm's test battery, where its every figure is reconciled against GitHub's API.
  • Adding a repository is one more invocation with a different repo argument; no ingestion and no configuration precede it.
